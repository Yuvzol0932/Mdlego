## 1. 状态栏顶到内容（状态栏空条 / 滚动缝隙）

- **提交**：`ce408d8` `fix(M2): 顶栏背景覆盖状态栏，消除空条与滚动缝隙`
- **现象**：Android 16 edge-to-edge 下，顶栏与状态栏之间有一条与主题不同色的空条；
  滚动时内容从那条缝里穿过去。目录抽屉与顶部搜索浮层同样被顶出屏幕。
- **根因**：`.shell` 用 `padding-top: var(--safe-top)` 把整页往下推，顶栏是 `sticky` 且
  `top: 0`，于是顶栏只贴在「被推下去之后的 0 位」，安全区那段没有任何元素覆盖，
  露出的是 body 背景。抽屉用 `margin-top: var(--safe-top)` 是同一个错误的另一种写法。
- **改法**：取消外壳的整体下推，改由顶栏自己吃安全区 ——
  `.appbar` 保持 `top: 0`，把 `padding-top: calc(var(--safe-top) + 原内边距)` 放进内部，
  背景就自然铺到屏幕物理顶部。抽屉改为在基类里吃 `padding-top`，不再叠 `margin`。
- **验证**：真实 Chrome 393×873 DPR3 三张图（静态 / 滚动中 / 搜索浮层），已由外部复核通过。

## 2. 阅读进度恢复错位（只恢复到「某一块的顶部」）

- **提交**：`78a93b3` `fix(M2): 阅读进度按顶栏下沿选块，恢复时扣掉顶栏高度`
- **现象**：退出重开能回到大致位置，但每次都比原位置高一截；且顶栏下沿常压住正文第一行。
- **根因**：两处叠加。一是记录时用 `article.top` 当基准，而它随内容一起上移、恒为负，
  导致「第一个块」总是满足条件，记下来的永远是块列表的第一个；二是恢复时按块顶对齐，
  没扣掉 sticky 顶栏的高度，目标块被顶栏遮住。
- **改法**：基准线改用 `appbar.getBoundingClientRect().bottom`（视口坐标，滚动时不变），
  取第一个 `rect.bottom > baseline` 的块；`scrollToBid()` 里减去顶栏下沿高度。
- **结果**：真机终验时发现「只能大概恢复」—— 块级精度不足以定位到行，遂进入第 3 项。

## 3. 阅读进度精度不足（只能恢复到块，落不到行）

- **提交**：`9cf41eb` `fix(M2): 进度精度到行内 ratio，恢复用 auto 滚动并等一帧`
- **现象**：长段落（超过一屏）退出重开时，只要还在同一段内，回到的永远是段落顶部；
  真机终验判为「只能大概恢复」。
- **根因**：`ReadProgress` 里有 `ratio` 字段，但 `persistProgress()` 恒写 `0`，
  恢复端也从不读它 —— 相当于只有块 id，进度精度止于块。
  另外恢复用 `'smooth'` 滚动 + 固定 `80ms` 等待，渲染未完成时平滑滚动会被打断。
- **改法**：
  1. `persistProgress()` 写 `(基准线 - rect.top) / rect.height`，钳制到 `0~1`；
  2. `scrollToBid(bid, ratio = 0, behavior = 'smooth')` 目标位置加 `ratio × 块高`；
  3. 恢复改 `behavior: 'auto'` + 双 `requestAnimationFrame` 等渲染完成，不再猜时序；
  4. 目录/搜索跳转不传 `ratio`，走默认 `0`，行为不变。
- **验证**：真实 Chrome，8051px 长段落滚到中部退出重开，顶栏下第一行前后一致（误差 0 行）；
  短块中段与文末两组前后截图逐字节一致；目录跳转目标未被遮挡。

## 4. 门禁回归（`check:selectors` 被第 3 项弄红）

- **提交**：`89a0b41` `fix(M2): 补回 check:selectors 门禁（进度提交引入的裸 .appbar）`
- **现象**：`npm run verify` 从 `9cf41eb` 起在 `check:selectors` 一步失败，两处 `.appbar`。
- **根因**：第 3 项需要在两个位置取顶栏下沿，直接写了 `querySelector('.appbar')`。
  该门禁禁止 `views/` 之外的层使用裸选择器。
- **改法**：抽一个 `appbarBottom()`，从 `[data-testid="app-title"]` 的父元素取顶栏，
  两处调用点共用。行为不变，门禁恢复绿色。

## 5. 系统返回键直接退出应用

- **提交**：`89a629c` `feat(M2): 接线系统返回键，返回顺序与应用内返回一致`
- **现象**：阅读中、设置页里按系统返回键，应用直接退出，而不是回到上一层。
- **根因**：`@capacitor/app` 8.0.1 一直在 `dependencies` 里，但全仓从未注册过
  `backButton` 监听。没有监听者时 Capacitor 走默认行为 —— 调 `WebView.goBack()`；
  而本项目是单页 hash 路由，历史栈里没有可回退的条目，于是等于退出。
- **改法**：注册 `App.addListener('backButton', handleSystemBack)`，
  按 `renderApp()` 的渲染优先级一次退一层：目录/搜索浮层 → 只关浮层；
  设置页 → 回 `#/`；排版浮层 → 只关它；阅读页 → 走 `doc/closed` 分发
  （订阅者先存进度再回书架）；书架页 → `App.exitApp()`。只在原生平台注册。
- **验证**：**待真机验**。浏览器没有硬件返回键，Chrome 测不了这一项。

## 6. 任务清单勾选不保存

- **提交**：`9b02cfe` `feat(M2): 任务清单勾选状态落库，重开与刷新都还在`
- **现象**：文档里的任务清单可以勾，但返回书架再打开、或刷新页面后，勾选全部丢失。
- **根因**：`data/db.ts` 里 `tasks` 表、`getAllTasks()`、`putTask()` 都齐全，
  但全仓没有一处调用。启动只 `loadShelf()`，`state.tasks` 恒为空；
  勾选只经过 reducer 改了内存状态，下一次重渲染又按空状态套回去。
- **改法**：只接线两处，不动 schema、`TaskState` 形状与渲染逻辑 ——
  1. 启动时经 data 层 `getAllTasks()` 灌进初始 state（读失败按空状态继续）；
  2. 拦截 `task/toggled`，先走原 `dispatch` 改状态，再 `putTask()` 单条写库。
- **验证**：真实 Chrome，勾选第 1、3 项 → 回书架 → 重开同篇仍在 → 刷新页面再开仍在；
  `tasks` 表里确有这两条记录。

## 7. 路由切换继承滚动位置

- **提交**：`240b8ab` `fix(M2): 路由切换时滚动归零，但避开阅读进度恢复`
- **现象**：阅读页滚到中部后进设置页，设置页停在同一个 `scrollY`，顶部三个 stepper 被顶出视口。
- **根因**：`hashchange` 只重渲染、不动滚动，滚动位置是文档级的，跨路由保留。
- **改法**：`hashchange` 里渲染后 `window.scrollTo(0,0)`，但用 `restorePending` 标记避开阅读页的进度恢复。
- **两个实施时踩到的坑（都已实测验证）**：
  1. 判 `currentDocId === null` 才归零 → 进设置页时该值仍非空，等于没修；
  2. 无条件归零 → 会盖掉 `openDoc()` 双 rAF 里的进度恢复，重开文档永远回顶部。
- **验证**：真实用户路径（点顶栏返回、点设置，不脚本改 hash）：阅读页 522 → 书架 0 → 设置页 0 → 重开文档 522。

## 8. 待处理 URI 失败后重复提示（结案：跨冷启动重试的前提不成立）

- **提交**：`645707a` `fix(M2): 同一条失败分享在同一进程内只提示一次`
- **原描述**：「待处理 URI 失败后每次启动重试弹同一 toast」。
- **查证结论：前提不成立。** 原生 `MdlegoNative.pendingUris` 是**进程内 ArrayList**，
  `am force-stop` 杀进程时随之清空。实测链条：
  - 投递读不到的 URI（应用在跑）→ pending 保留该 URI，弹「1 篇失败 · 没有读取该文件的权限…」；
  - `force-stop` + 冷启动 → `peekPendingUris()` 返回 `[]`，无 toast。
  审计时看到的那次 toast 是同一次冷启动内真实失败留下的残留，不是跨启动重试。
- **仍然修掉的一个真实场景**：应用在后台收到 `onNewIntent`（同一份文件被再次分享）会重复触发
  `consumePendingShare`，同一条坏 URI 每次都重新读取、重新失败、重新弹同一条提示。
  改法：进程内 `failedPendingUris` 集合，失败过的 URI 本进程内不再读、不再弹；进程重启后仍会重试一次。

## 9. 排版浮层死分支

- **提交**：`292c9e8` `refactor(ui): 删除 font 排版浮层死分支`
- **现象**：`state.overlay === 'font'` 有渲染分支，但界面上找不到任何入口。
- **根因**：全仓唯一派发 `overlay/opened` + `'font'` 的代码，就在那条分支自己渲染的「完成」按钮里，
  即「只能关自己、无法被打开」。排版控件在设置页有完整入口，该分支纯冗余。
- **删除范围**：`views/app.ts` 的分支、`views/settings.ts` 的 `fontOnly` 参数与相关三元、
  `core/types.ts` 的 `OverlayKind` 去掉 `'font'`、`state/store.test.ts` 两条断言改用 `'toc'`。
- **验证**：四道门禁全绿、`tsc --noEmit` 无错、`vitest 206 passed`、真机设置页与返回键正常。
