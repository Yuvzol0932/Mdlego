# 墨读 Mdlego · 开发规范

> 目标只有一条：**避免「改一处动十处」**。
> 所以下面每一条规范都必须能被机器检查 —— 写进文档但无法执行的规范，等于没有。

## 0. 总则

**一切以效果为主，反对教条主义与形式主义。**

判断一条规范该不该留，只问一个问题：它有没有真的挡住过一次事故？
如果一条规则只增加仪式感而不减少事故，删掉它。

---

## 1. 契约先行

**先写 `core/types.ts` 里的类型，再写实现。**

跨层传递的每一种数据都必须在 `core/types.ts` 有具名类型。禁止 `any`、禁止匿名内联结构在层间流动。

- **利**：模块边界在编译期被钉死，改了一边另一边立刻报错。
- **弊**：起步慢半天。
- **执行**：`tsc --noEmit` 进 `npm run verify`；`strict` + `noUncheckedIndexedAccess` 全开。

---

## 2. 依赖单向

```
views → ui → core
views → data → core
core  不依赖任何上层
```

- `core` **禁止** import `data` / `views` / `ui`（例外：`core/selection.ts` 可读 DOM，但不得 import 上层模块）。
- `views` **禁止**直接使用 `indexedDB`、`localStorage`、`fetch`、`Capacitor`。
- `data` **禁止** import `views`。

- **利**：改一层不会炸另一层。
- **弊**：偶尔要为「顺手想直接调」的冲动多写一层中转。
- **执行**：`npm run check:boundaries`，用 TypeScript 编译器 API 解析真实 import 图，违规即失败。

---

## 3. 单一状态树

所有业务状态住在 `state/` 的一个对象里。视图**只读**，变更只有一条路：

```
dispatch(action) → reducer(state, action) → 新 state → render(state)
```

- **利**：状态来源唯一，bug 可定位；时间旅行调试可用。
- **弊**：写起来比直接改对象啰嗦。
- **执行**：`npm run check:state`，禁止 `views/` 与 `ui/` 中出现 `state.<字段> =` 这类赋值。

---

## 4. 选择器集中

JS 会操作的节点统一带 `data-testid`。测试与实现通过 `data-testid` 接头，而不是 CSS 类名或结构位置。

- **利**：改 DOM 结构与样式不需要改测试。
- **弊**：多敲几个字符。
- **执行**：`npm run check:selectors`，禁止在 `views/` 之外出现裸 `querySelector('#')` / `querySelector('.')`。

---

## 5. 设计令牌单一来源

颜色、字号、间距、圆角、阴影**只允许**定义在 `web/src/styles/tokens.css`。

- **利**：换主题一处改完；不会出现「同一个蓝色有七种写法」。
- **弊**：初期要克制随手写十六进制色值的冲动。
- **执行**：`npm run check:tokens`，扫描 `app.css` 与 `.ts` 中的硬编码色值，违规即失败。

---

## 6. 版本单一来源

`package.json` 的 `version` 是**唯一**版本事实源。

- Gradle 构建时读它生成 `versionCode` / `versionName`。
- Vite 通过 `define` 注入 `__APP_VERSION__`。
- 每次构建写入 `buildId = git短哈希-时间戳`，显示在设置页。
- 打包后用 `aapt2 dump badging` **反读 APK**，与 `package.json` 不一致即失败。

- **利**：彻底消灭「装了没变化」这类问题的全部可能。
- **弊**：每次打包多约 10 秒。
- **执行**：`npm run android:build` 内置校验；`npm run android:verify` 可独立复核已装机版本。

> 上一代项目版本号散落在 6 个地方（build.gradle、package.json、index.html、sw.js、app.js、MainActivity），
> 只能靠「版本位点门禁脚本」互相追赶，结果还是出现了两次「覆盖安装看不到变化」。本项目从结构上消除这个可能。

---

## 7. 每次修复留三段证据

任何 bug 修复必须留下三段可核对的东西：

```
输入：做了什么操作
现象：看到了什么（截图 / 日志 / 断言输出）
结果：修好后现象变成了什么（截图 / 日志 / 断言输出）
```

提交信息里必须含 `Evidence:` 段落。

- **利**：不做「应该好了」的自欺。
- **弊**：每轮多花几分钟。
- **执行**：`tools/check-commits.mjs` 对 `fix:` 前缀的提交提示缺失证据。

---

## 8. 一步一提交

一个逻辑改动一次提交，提交信息写**为什么**，不写「改了什么」（改了什么看 diff 就知道）。

- **利**：可单点回退；回溯时能看懂当时在想什么。
- **弊**：提交条数变多。

---

## 9. 测试必须能证明你在乎的那件事

**禁止用 mock 冒充真机场景。** 上一代项目 60 项测试全绿，却漏掉了真机上「划词工具条不出现」，
因为这些测试全部在同一个段落内构造选区 —— 而手指一拖几乎必然跨块。

规则：

- 涉及选区的测试**必须**构造：跨块、跨表格单元格、起点为容器元素的选区。
- 涉及渲染的测试**必须**断言真实 HTML 输出，而不是断言「函数被调用过」。
- 关键流程**必须**在真实 Chrome（移动尺寸 + 触摸模拟）与 Android 模拟器上跑一遍。

- **利**：能在交付前抓住真机类 bug。
- **弊**：写测试慢 2–3 倍。
- **执行**：`npm run verify`（单元 + 类型 + 构建）；`npm run smoke`（真实 Chrome）；`npm run android:install`（模拟器）。

---

## 10. 提交前检查清单

```
□ npm run verify        全绿（边界 + 令牌 + 选择器 + 状态 + 类型 + 测试 + 构建）
□ npm run smoke         真实 Chrome 移动尺寸通过
□ 涉及 UI 的改动         有截图
□ 修复类提交             有 Evidence 段落
```

---

## 11. 这些规范不做什么

- 不要求写「覆盖率 80%」这种数字指标 —— 覆盖率不反映测试是否证明了正确的事。
- 不要求每个函数都写注释 —— 只在「为什么这么做」不明显时才写。
- 不要求固定的文件命名风格 —— 只要求同一目录内一致。
- 不禁止重构 —— 但重构必须是独立提交，且 `npm run verify` 全程绿。
